## 0. 一句话结论

v1.4.x 对我们**不是一次协议破坏性升级**。Conscrypt 是 Android 侧 TLS 实现替换，与我们无关；ECDH 信封格式未变。需要动手的实际只有三类：

| 类别 | 项数 | 性质 |
|---|---|---|
| P0 必须适配 | 1 | NCUID 写入侧收敛为双写（新 diff §7 字段映射 + §15.3 兼容策略已坐实，旧/新/混合三模式均工作） |
| P1 新增能力缺口 | 5 | 消息搜索、群增量同步、歌词、播放列表/同步、表情搜索 |
| P2 观察确认 | 4+1 | 注册流程、Conscrypt、ECDH、B站模块；+ 媒体 OSS（当前不触发，files.mcl0 已移除） |

## 1. P0 — 必须适配

### 1.1 媒体/文件服务器（OSS / files.mcl0）

> **更新（2026-08-09，两点）**：
> (a) 腐竹确认后端当前返回**相对路径**、客户端动态解析，不返 OSS 绝对地址；OSS 能不用就别用 → **当前不触发**，降为观察项。
> (b) 新 diff §11 显示 `files.mcl0.dpdns.org` 在 v1.4.x **已被移除** → 我们 `MEDIA_URL_CANDIDATES` 里的该项属过期候选，可删；当前媒体走 `60.205.94.101:8080` 动态解析，无影响。
> 仍建议保留 capabilities 补 OSS 域名作为廉价保险（万一后端未来返绝对地址，可避免 plugin-http 静默拒绝）。

**文档依据**：新 diff §11（文件服务器 URL 变化）、02 文档 §5

| 类型 | v1.3.61 | v1.4.x |
|---|---|---|
| 文件服务 | `https://files.mcl0.dpdns.org/` | `http://oc.mcl0.dpdns.org` |
| OC 服务 | `https://oc.mcl0.dpdns.org` | `http://oc.mcl0.dpdns.org/v1` |
| OSS 存储 | — | `https://ocf.oss-cn-shanghai.aliyuncs.com/` **（新增）** |
| OSS 存储(HTTP) | — | `http://ocf.oss-cn-shanghai.aliyuncs.com/` **（新增）** |

**我们的现状**

```javascript
// app.js L199-200
const DEFAULT_BACKEND_ORIGIN = 'http://oc.mcl0.dpdns.org';   // ✅ 已经是新地址
const DEFAULT_MEDIA_ORIGIN   = 'http://60.205.94.101:8080';  // 源站 IP，暂时有效

// app.js L251-256 —— 绝对 URL 直接透传，不做任何域名处理
function resolveMediaUrl(url) {
    if (/^(https?:|data:|blob:)/.test(url)) return url;   // ← OSS 绝对地址走这里
    if (MEDIA_BASE && url.startsWith('/')) return MEDIA_BASE + url;
    return url;
}
```

**故障链条（这是真正的坑）**

后端一旦开始在 `media_url` 里返回 OSS 绝对地址，`resolveMediaUrl()` 会原样透传 —— 逻辑上没问题。但请求会被 **Tauri capabilities 拦在门外**：

```jsonc
// src-tauri/capabilities/default.json —— 当前白名单
"allow": [
  { "url": "http://oc.mcl0.dpdns.org/**" },
  { "url": "http://60.205.94.101:8080/**" },
  { "url": "http://60.205.94.101/**" },
  { "url": "http://files.mcl0.dpdns.org/**" },
  { "url": "https://**" }        // ← https OSS 侥幸被覆盖
]
```

`https://ocf.oss-...` 被 `https://**` 兜住了，但 **`http://ocf.oss-...` 没有任何一条匹配** → plugin-http 直接拒绝 → 图片/语音/视频**静默加载失败**，且报错信息不直观（不是 404，是权限拒绝），排查成本很高。

**需要改的三处**

1. `capabilities/default.json` 补 `http://ocf.oss-cn-shanghai.aliyuncs.com/**`（https 那条虽被通配覆盖，建议显式写出便于审计）
2. `MEDIA_URL_CANDIDATES`（L210-216）补 OSS 域名
3. **容易漏掉的一处**：媒体缓存层 `mediasOriginSet`（L477-480）只收录 `MEDIA_ORIGIN` + `BACKEND_ORIGIN`：

```javascript
mediasOriginSet = [ MEDIA_ORIGIN, BACKEND_ORIGIN ].filter(Boolean);
```

OSS 域名不在其中 → OSS 上的图片**不会进 IndexedDB 永久缓存** → 每次打开聊天都重新走网络。功能不报错，但流量和体验劣化，而且这类问题没人会主动发现。

> 补充：`files.mcl0.dpdns.org` 是付费 CDN（项目既定约束是尽量少用）。v1.4.x 官方把它换成 OSS，方向上和我们的节流诉求一致，迁移动力充足。

### 1.2 NCUID 写入侧内部不一致 ⚠️

**文档依据**：diff §9（NCUID 全面迁移，11 个字段）、03 文档 §10.1/§11.1/§12.3

**我们的现状——读写口径已经打架了**

```javascript
// app.js L1262-1269 —— 写入侧：只发旧字段
function toUidParam(id)   { return { to_uid: id }; }
function withUidParam(id) { return { with_uid: id }; }

// app.js L4319 / L4520 —— 读取侧：已经用新参数
`/v1/direct/messages/v2?with_ncuid=${...}`
```

同一个会话，拉历史用 `with_ncuid`、标记已读用 `with_uid`（L2273/L2294/L4489）、发消息用 `to_uid`（L5668/L6139/L6225）。目前能跑，是因为后端对 `to_uid`/`with_uid` 做了双向兼容（我们代码注释里也记着这一点）。但 diff §9.5 明确写了后端的迁移终局：

> **判断**：预计未来版本将完全移除 UID 支持。

**建议动作**：按官方的**双写双读**策略收敛，两个字段一起发，让后端自己挑：

```javascript
function toUidParam(id)   { return { to_uid: id, to_ncuid: id }; }
function withUidParam(id) { return { with_uid: id, with_ncuid: id }; }
```

这样新旧后端都吃得下，且未来后端摘掉 uid 时我们零改动。

**⚠️ 文档自身存在矛盾，落地前必须实测**

新文档在这一点上前后打架，不能盲信：

| 位置 | 说法 |
|---|---|
| 03 文档 §2.4 | 「历史查询: 仍建议使用 `with_uid` 作为兼容方案」 |
| 03 文档 §11.1 | 示例直接写 `GET /v1/direct/messages/v2?with_ncuid=<NCUID>` |
| 03 文档 §2.2 表格 | 消息历史查询 `?with_ncuid=` 标注 **"⚠️ 待验证"** |

我们线上跑的是 `with_ncuid` 且工作正常（L4319），说明 §11.1 是对的、§2.4 的说法已过时。发送 `to_ncuid`、已读 `with_ncuid` 同样被标为「待验证」，**双写方案的价值正在于绕开这个不确定性** —— 不用赌哪个字段对。

**同一议题下无需改动的一处**：`mentions` 字段名文档也自相矛盾（§4.2 示例用 `uid`，§4.3 字段表要求 `ncuid`）。我们 L5633 已经是两个都写：

```javascript
mentions.push({ uid: ..., ncuid: ..., name: member.name });
```

已经是最稳形态，**保持现状即可**，不要"按文档改成只发 ncuid"。

## 2. P1 — 新增能力缺口

原版有、我们没有。不影响现有功能，属于排期项。

### 2.1 消息搜索（2 个新端点）

```
GET /v1/direct/messages/search?with_uid=<UID>&keyword=<关键词>
GET /v1/groups/messages/search?group_id=<GID>&keyword=<关键词>
```

**现状**：完全没有（`grep messages/search` 无命中）。

**意义**：`docs/gap-analysis.md` 里「全局搜索缺失」曾被列为 P1，当时的判断是"后端无端点、做不了"。**现在后端把端点交出来了，这条从"做不了"变成"可以做"** —— 是本次 diff 中对我们价值最高的新增。

### 2.2 群消息增量同步

```
GET /v1/groups/messages/after?group_id=<GID>&after=<时间戳>
```

**现状**：只有 offset 分页全量拉取（L4318/L4519）。

**意义**：现在 WS 断线重连后，中间漏掉的群消息没有可靠补齐手段 —— 靠 offset 翻页去对齐存在消息空洞风险。这个端点正是为此设计的，建议接入重连恢复流程，属于**修复既有隐患**而不只是加功能。

### 2.3 音乐系统（缺口最大）

我们只有 `plaza` / `ranking` / `mine` 三个 tab（L1393-1395）。v1.4.x 的音乐模块已扩成完整生态：

## 3. P2 — 观察确认（大概率无需动作）

### 3.1 Conscrypt TLS —— 明确无需适配 ✅

diff 把 Conscrypt 列为「影响级别：**高**」，容易让人误以为我们也要跟。**实际对我们零影响**：

- Conscrypt 替换的是 **Android 系统默认 TLS 实现**，解决的是「不同 Android 版本 TLS 行为不一致」
- 我们走 Tauri `plugin-http`（Rust `reqwest` + rustls/native-tls），根本不在这条链路上
- 且后端当前是 **HTTP 明文**（`http://oc.mcl0.dpdns.org`），连 TLS 都没启用

> 在此明确记录，避免后续接手者看到「高影响」就去折腾 TLS 配置。

### 3.2 ECDH 握手协议 —— 未变更 ✅

对比 08 文档 git diff：改动仅为标题版本号、把 TLS 层描述从「HTTPS」换成「Conscrypt TLS」、新增一张 v1.4.x 安全层对比表。**握手流程、密钥派生、信封格式（`{iv, data, mac}`）全部未动**。

我们 app.js L3270-3407 的 ECDH P-256 + AES-CBC + HMAC-SHA256 实现继续有效，无需改动。

### 3.3 注册流程 —— 需回归测试

diff §11.1：`RegisterActivity` 在 v1.4.x 被移除。

我们 login.html L558 用的是 `/v1/auth/web/register`（**web 专用端点**，与 Android 的注册路径本就不同），加上 GeeTest 验证码 + 邮箱验证码流程。判断**大概率不受影响** —— Android 端移除的是它自己的 Activity，不代表 web 端点下线。

**动作**：不改代码，但纳入回归测试清单，实测一次注册全流程。若失败，参考 diff §11.1 给的三种可能（整合进 login / 独立 `/register` 端点 / 手机号验证码）。

### 3.4 B站模块 —— 缺口加深，但不构成新负担

v1.4.x 对 B站模块做了完整重构：`BiliWbiSigner`（Wbi 签名算法）、`BiliAuthStore`、`BiliQrGenerator` 等 7 个类 + 40 余个数据模型，覆盖收藏/历史/评论/推荐。

我们**本来就完全没有 B站集成**（gap-analysis 列为 P0 完全缺失）。这次重构不影响现有功能，只是把补齐门槛抬高了 —— 新增的 Wbi 签名是 B站官方反爬机制，若要实现需额外处理密钥获取与参数签名逻辑。

**建议**：维持"暂不实现"判断。这属于第三方增值功能，优先级低于 IM 主链路。
