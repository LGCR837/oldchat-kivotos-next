## OldChatCRTerminal：修复 neo-blessed Tab 焦点环（重要踩坑）
- 现象：Tab 切不动（弹回原框）+ 每按一次 Tab，之后每敲一个键就重复输入 N 个字符。
- 根因（读 node_modules/neo-blessed/lib/widgets/textarea.js 定位）：
  1. **textarea.js:175** —— 只要 textbox 开了 `inputOnFocus:true`，失焦时 `_done()` 末尾会调 `screen.rewindFocus()`，把焦点弹回 history 上一个元素，跟手动 `focus()` 打架（screen.js:1642 rewindFocus + 1660 _focus 会级联 blur/focus）。
  2. **textarea.js:200** —— `readInput()` 在 `nextTick` 里才 `self.__listener = self._listener.bind(self); self.on('keypress', ...)`，而 `_done()` 在同一 tick 同步 `removeListener('keypress', self.__listener)`；此时 `__listener` 还是 undefined，移除是空操作 → 下个 tick 两次 attach 都生效 → keypress 监听器逐轮累加 → 输入成倍重复。
  3. 附带：`_listener` 的字符过滤正则是 `/^[\x00-\x08\x0b-\x0c\x0e-\x1f\x7f]$/`，**不含 \x09**，所以 Tab 会被当普通字符插进 value。
- 解法（`src/focus-ring.js`，新建；`src/main.js` 改用它）：
  - 所有 textbox 一律 `inputOnFocus:false`，由焦点环自己驱动：`focus(i)` = 先 `prev._done(null,null)` 干净收尾 → `el.focus()` → 若是 textbox 再手动 `el.readInput()`。彻底绕开 rewindFocus 与同 tick 竞态。
  - Tab **必须绑元素级**（`el.key(['tab'])`）：readInput 期间 `screen.grabKeys=true`，screen.js:591 会跳过 screen 级按键，只有 601 行的 `focused.emit('key '+full)` 还会走。
  - 覆写 `tb._listener` 吞掉 `key.name==='tab'`（幂等，`__tabBlocked` 标记防重复包裹）。Shift+Tab 的 key.full 是 `S-tab`。
  - 非输入元素（按钮）聚焦时 `program.hideCursor()`，光标不再乱跑。
- 验证：新增 `test-focus.js` —— 用假 TTY（Writable/Readable 打 `isTTY`）构造 screen，直接往 `screen.program.emit('keypress', ch, key)` 打事件做无终端断言，17 项全过（含"转两圈后监听器仍为 1"）。`npm test` 串联 smoke-test + test-focus。
- 经验：neo-blessed 的 `inputOnFocus` 与任何自定义焦点管理天然冲突；多输入框表单要么用官方 `blessed.form({keys:true})`，要么像这里自管 readInput，别混用。

## OldChatCRTerminal：Windows Terminal 鼠标彻底失效的根因（终版修复）
- 现象：聊天界面在 Windows Terminal 下鼠标"点不动也滚不动"。前几轮修（控件级 mouse、screen 级 onScreenMouse 按 lpos 命中测试、强制 setMouse）都无效——根因不在路由，而在"终端压根没收到鼠标启用序列"。
- 定位（读 node_modules/neo-blessed/lib/program.js）：
  1. `enableMouse()`（行 3313）靠 TERM 探测（xterm/screen/linux/isVTE），**TERM 为空时整个函数走末尾直接 return，连 `?1002h`/`?1006h` 序列都不发** → 终端不上报鼠标。
  2. 即使手动 `program.setMouse({sgrMouse:true,cellMotion:true}, true)`，库内部 `setMode` 走 **tput 间接层**，TERM 空时 tput 完全无输出 → 序列到不了终端（本地 mock 验证：setMouse 后 collected 查不到 `?1002h`）。
  3. 解析层本身是好的：直接喂 SGR 序列 `\x1b[<0;10;5M`，`screen.on('mouse')` 能正确收到 `{action:'mousedown',x,y}`。所以"假 TTY 验证通过"只验证了解析、没验证启用序列——这是之前反复修不好的盲点。
- 终版修复（`src/main.js`）：**不依赖 blessed 的 enableMouse/setMouse，直接、确定性地写原始 CSI**：
  - `function ensureMouse(){ process.stdout.write('\x1b[?1002h\x1b[?1006h'); }`（?1002h=cell-motion 跟踪，?1006h=SGR 编码；XTerm 鼠标协议事实标准，Node `process.stdout.write` 必送达）。
  - alt-screen 已激活后调用：`enterChat` 内 `buildChatUI()` 之后 `ensureMouse()`；并 `screen.on('render', ensureMouse)` 对抗 alt-screen 切换/resize 重置（幂等无害）。
  - 另设 `process.env.BLESSED_FORCE_MODES='SGRMOUSE=1,CELLMOTION=1'`（行 6）作双保险，让库自身 enter 流程也走 force 分支。
  - 路由仍用已工作的 `screen.on('mouse', onScreenMouse)`（滚轮滚聊天区、左键点侧边栏切会话、处理后 `enterInput()` 夺回焦点）。
- 教训：blessed 鼠标在现代终端（尤其 Windows Terminal / TERM 空）不可靠，凡涉及鼠标启用一律直接写原始 `\x1b[?1002h\x1b[?1006h`，别信 enableMouse/setMouse。验证启用序列是否真发出，必须捕获真实 stdout 写入（mock output 会被 tput 绕过，骗自己）。
- 补充（同轮）：聊天界面 sidebar/chatLog/input 的 `mouse:true` 必须**全部移除**——否则 blessed 控件级 mouse 会让侧边栏被滚轮异常滚动、并把焦点从输入框抢到侧边栏（"回不去"）。鼠标统一走 screen 级 `onScreenMouse` 后，控件级 mouse 纯副作用。另加 `refocusInput()`：每次鼠标交互后 `if (screen.focused !== input) enterInput()`，确保焦点始终锁输入框。
- 环境：Windows Terminal + Node 22，`npm start`。用户说过"别测试了"——只做 node --check + 本地单测，不连真后端验证。

## OldChatCRTerminal：中文/Emoji 多了大量字符错位 + 凭空显示残影（根因与修复）
- 现象：消息里中文和 Emoji 一多，界面字符整体错位，并出现不属于当前内容的残影字符。
- **根因**：neo-blessed 的 `lib/unicode.js` 宽度表基于旧版 Unicode，**完全没有现代 Emoji 区间 U+1F300–U+1FAFF**（表里只有 U+1F200–U+1F251 这类带圈日文 + CJK 扩展）。于是 😀 被算作 **1 列**，而 Windows Terminal 实际渲染 **2 列** → 每个 Emoji 偏 1 列；反向地，变体选择符 U+FE0F、ZWJ U+200D 等 blessed 算 1 列、终端占 0 列。正负偏移累积 → 整行错位；blessed 差分渲染又不重绘「它以为没变」的单元格 → 残影。
  - 实测断言（`test-wide-text.js` 第 7 组）：打补丁**前** `unicode.charWidth('😀',0) === 1`，打补丁后 === 2。这条直接坐实根因。
- **修复（两层，新增 `src/wide-text.js`）**：
  1. `patchUnicode(require('neo-blessed/lib/unicode'))` —— 运行时替换 `unicode.charWidth`，补齐 Emoji_Presentation=Yes 区间返回 2、零宽字符返回 0，其余委托原实现。**可行的关键**：blessed 内部是 `unicode.charWidth(...)` 属性查找调用（`widgets/screen.js:1293/2166` 绘制、`widgets/element.js:2546` 自动换行），所以替换模块导出即全局生效，**无需改 node_modules**；`strWidth` 内部也调 `exports.charWidth`，一并被修正。必须在任何渲染前 patch。
  2. `sanitize()` —— 剔除宽度**不可预测**的字符：VS15/VS16(FE00-FE0F)、ZWJ(200D)、肤色修饰(1F3FB-1F3FF)、Keycap(20E3)、零宽(200B/200C/2060/FEFF/00AD)、控制字符(保留 \t\n)、CRLF 归一；国旗（区域指示符对）转 `[CN]` ASCII。
     - **为什么必须有第 2 层**：VS16 会改变**前一个**字符的宽度，单字符宽度函数在原理上无法表达；ZWJ 序列在不同终端可能合并渲染 2 列或拆开渲染 6 列，同样不可预测。只能提前剔除，让双方判断必然一致。
- 接入 `src/main.js`：`safe()` = `wideText.sanitize()` + `{}`转义；`strW()` 改用 `wideText.dispWidth`（不再用 `screen.strWidth`）；`truncate` 直接用 `wideText.truncate`（按列数截断且不劈开代理对）；`flash()` 的服务端提示也过 `safe()`。
- 残影兜底：`forceRedraw()` = `screen.realloc()` + `program.clear()` + `render()`（realloc 重建 lines/olines 使差分渲染失效 → 全量重画）。绑定 `Ctrl+L`（输入态经 key-router 新增 `redraw` 动作 + input-attach `onRedraw` 分发，否则会被 textarea 吞成字符）与 `screen.on('resize')`。
- 验证：`test-wide-text.js` 45 项全过（含"打补丁后 blessed 与自研 dispWidth 对混排样本判断完全一致"）；test-focus/test-chat(31)/test-chat-ui(16) 回归全绿；`npm test` 已串入新测试，另加 `test:ui`/`test:width` 脚本。
- 已知残留：**输入框里用户正在打的 ZWJ 组合 Emoji** 不走 sanitize（清洗会打乱编辑光标），单个 Emoji 已正确、ZWJ 序列仍可能微错位，Ctrl+L 可修。
- 教训：TUI 里凡是要按列数排版的地方，绝不能信任 blessed 自带的 `screen.strWidth`/`unicode.charWidth`；Emoji 宽度问题必须「修正宽度表 + 提前剔除不可预测字符」两层一起做，只做任一层都会残留错位。

## 主项目：修复「连消息」分组偶发错乱（src/app.js）
- 现象：同发送者、5 分钟内的连续消息偶尔「该连没连」；对方消息偶尔「中间隔一个（自己的未确认消息）也被当连消息」。
- 根因（连消息是增量式判定，只比对模块态游标 `lastRenderedMsg`/`lastRenderedTs` 与「上一条渲染消息」）：
  1. **Bug「隔一个被连」**：`appendMessage` 末尾曾刻意让 `temp_` 临时消息（自己发的、发送中半透明占位）**不推进**游标 → 游标停在前一条对方消息；下一条对方消息误与前一条连组，跳过自己那条。

## 上一轮 #5/#6 的两处回归修正（2026-08-11 傍晚）
用户实测反馈：其他页面好了，但①聊天最大化图标不切还原、②用户空间三大金刚键"按不动"。根因：
1. **聊天最大化回归**：上一轮把 `syncMaximizeState` 的选择器写成 `[id$="WinMaxBtn"]`，但**聊天按钮 id 是 `winMaxBtn`（小写 w 开头）**，不匹配 `WinMaxBtn` 后缀 → 聊天按钮反而漏掉、不再切图标。修正为 `[id$="MaxBtn"]`（9 个 MaxBtn 结尾的 id 全是最大化按钮，安全）。
2. **用户空间"按不动"根因（重要）**：`openSpacePanel` 在 `DOMContentLoaded` 回调作用域（行 2101 起），而 `invoke` / `syncMaximizeState` 定义在**另一个作用域**——`initTauri` IIFE（行 13–202）。跨作用域拿不到，点击时 `invoke(...)` / `syncMaximizeState()` 直接抛 `ReferenceError` → 什么也不发生。音乐面板的窗口控制（行 2781）专门重新声明了 `tauriInvoke` 就是因为这个坑。**结论：凡是写在 `DOMContentLoaded` 作用域里的窗口控制绑定，必须用 `window.__TAURI__?.core?.invoke`，不能用 IIFE 里的 `invoke`。**
   - 修正：用户空间绑定改用本作用域解析的 `spInvoke = window.__TAURI__?.core?.invoke || window.__TAURI_INTERNALS__?.invoke`，最大化图标同步改为内联 `spSyncMaxIcon()`（不依赖越界的 `syncMaximizeState`），并删除原来的 `syncMaximizeState()` 调用。
- 验证：`node --check src/app.js` 通过；`[id$="MaxBtn"]` 经全量 id 枚举确认只命中 9 个最大化按钮、无误伤 MinBtn/CloseBtn。GUI 视觉未验，需 `npm run tauri dev` 实测。
