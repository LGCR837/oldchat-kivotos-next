## 【严重回归 + 修复】候选降级把 `/v1` 前缀吃掉，全部接口 404

**现象**：用户实跑后所有联网列表全挂，控制台刷屏
`SyntaxError: Failed to execute 'close' on 'ReadableStreamDefaultController': Unexpected non-whitespace character after JSON at position 4 (line 1 column 5) at Object.pull (app.js:101:36)`
（WS init / loadContacts / loadMusicList 全中）。

**根因（已 100% 坐实，非猜测）**：
- 旧代码：`fetch(API_BASE + url.slice(3))`，其中 `API_BASE = BACKEND_ORIGIN + '/v1'` → `origin` + `/v1` + `/me` = `origin/v1/me` ✅
- 我改的 `_fetchWithCandidates`：`fetch(base + url.slice(3))`，而 `BACKEND_CANDIDATES` 存的是**裸 origin（不含 /v1）** → `origin` + `/me` = `origin/me` ❌ **`/v1` 被吃掉**
- 后端（Go + nginx）对未知路由返回 `404 Not Found`，`Content-Type: text/plain`，body 正是 `404 page not found\n`
- `JSON.parse("404 page not found\n")` 的报错逐字为 `Unexpected non-whitespace character after JSON at position 4 (line 1 column 5)`（`404` 解析成数字→index 3 空格→index 4 的 `p` 越界）
- 报错**显示在 `controller.close()`（app.js:101）**是障眼法：Chromium 的 `Response.json()` 是原生实现，在流 close 那一刻同步解析累积字节，JSON 异常被 DOM binding 包装成 `Failed to execute 'close' on 'ReadableStreamDefaultController': <JSON错误>`。**与 Tauri sentinel 字节协议、`res.clone()` 去重都无关**（两者均已单独验证正确，官方 plugin-http 2.5.9 的 Rust `fetch_read_body` 协议确认为 `数据+[0]` / EOF `[1]`，我们的 wrapper 与之一致）。

**实证**：
- `curl http://oc.mcl0.dpdns.org/friends` → 404 text/plain `404 page not found`
- `curl http://oc.mcl0.dpdns.org/v1/friends` → 401 application/json ✅（60.205.94.101:8080 同样表现，两候选均正常）

**修复（src/app.js）**：
1. `_fetchWithCandidates`：`fetch(base + relPath)` → **`fetch(base + url)`**（url 本身已含 `/v1`），删除 `relPath`；401 refresh 后重试同样改为 `base + url`。
2. refresh 端点 `BACKEND_CANDIDATES[0] + '/auth/refresh'` → **`+ '/v1/auth/refresh'`**。
3. 新增 `_normalizeOrigin()`，`_parseCandidates` 统一归一化候选：去结尾 `/`、去误加的 `/v1`、并去重保序 —— 防止用户在设置页粘贴 `http://x/v1/` 再次触发同类问题。
4. 5xx 降级前 `res.body.cancel()`，避免流悬挂。
5. 新增诊断：非 JSON 的 404 直接 `console.error('[apiFetch] 路由不存在（非 JSON 404）…' + base + url)`，下次同类问题一眼可见。

**教训（重要，务必记住）**：
- `BACKEND_CANDIDATES` / `MEDIA_CANDIDATES` 的约定是**裸 origin，绝不含 `/v1`**；拼接一律 `base + url`（url 带 `/v1`）。`API_BASE` 现已无调用方，仅保留兼容。
- 见到 `Failed to execute 'close' on 'ReadableStreamDefaultController': Unexpected non-whitespace character after JSON at position N` 时，**先怀疑响应根本不是 JSON（多半是 404/502 的纯文本或 HTML），而不是流/克隆/sentinel 协议**。`position 4` 基本就是 Go 的 `404 page not found` 指纹。
- 媒体降级 `MEDIA_CANDIDATES[i+1] + src.slice(base.length)` 是整段换 base、保留原路径，无此问题。

## 调研：首页列表「折叠群组」是本地还是联网同步

**结论：纯本地 UI 偏好，不联网同步**（逆向文档未逐条写该功能，但架构证据链完整、可定论）。

证据：
1. `mcl0/client.md` §7.1 `ChatsFragment` 分段 = News / Chats / **Folded（折叠的旧会话）**；该分段由 `RecentChatBuilder.buildCombinedList(app, unreadNotifications)` 在**客户端本地**合并算出，数据源只有 `RecentChatCache` + `GroupRecentChatCache` + 系统通知，全程无服务端「折叠」字段参与。
2. `mcl0/client.md` §12.1 SharedPreferences 清单：`settings` SP = `server_base_url / files_server_base_url / 夜间模式 / DPI / `**`首页设置`** —— 与主题、DPI 并列，典型纯本地 UI 偏好。
3. 服务端 `routes.md` 共 **190 条路由，无任何用户级偏好/折叠/置顶/归档接口**。`/v1/me/*` 全是 checkin / presence / devices / profile / avatar / cover / uid / password，没有 preferences。
4. 易混淆项已排除：`POST /v1/groups/settings` = 群管理员改**群配置**（全群生效）；v1.4.x 的 `PUT /friends/settings` = **单个好友**备注/设置。都不是「我的首页折叠状态」。
5. WS 事件只有 `direct_message` / `group_message` / presence / recall，**无偏好同步推送**。

推论：Android 端换设备/重装即丢失折叠状态。我们的 Tauri 端实现直接用 localStorage 即可，与 Android 端天然各存各的、不会冲突。

## 登录 429 修复（握手风暴 + 自动登录失败抑制）

- **现象**：用户报"没法登录了 too many requests" + `[TAURI] Couldn't find callback id`（页面 reload 时 Rust 异步 invoke 未完成，良性）。
- **根因 1（app.js）**：`ensureWsSession` 无并发锁——v2 迁移后 apiFetch 对每个 /v2/ 请求都先 `v2SignHeaders()` → `ensureWsSession()`，启动时多个并发 v2 请求会**并发触发多次 ECDH handshake**（handshake 风暴）→ 后端限流 → 连带登录也 429。修复：`wsHandshakePromise` 单例共享握手 Promise（`.finally` 重置），并发调用只握手一次。
- **根因 2（login.html）**：autoLogin 每次页面加载自动提交登录，reload 循环会持续打 `/v1/auth/login` 触发 429。修复：登录失败（429/网络/解析错误）时 `sessionStorage.setItem('oc_auto_login_blocked','1')`，本会话内 autoLogin 跳过自动提交；登录成功清除标记。429 显示"请求过于频繁，请稍后再试"。
- 登录页独立（不引 app.js、不走签名/v2），登录请求本身未被迁移影响。
- 验证：node --check OK。待回归：等限流窗口过后重新登录；v2 请求握手只发一次（DevTools Network 看 handshake 数量）。

## v2 401 排查（第二轮：GET 误设 X-Enc + 401 响应体诊断）

- **现象**：用户实测 v2 仍 401 熔断，日志显示全是 **GET 请求**（/v2/groups/list、/v2/friends、/v2/friends/requests）。
- **疑点 1（已修）**：apiFetch 对**所有** v2 请求（含 GET）都设 `X-Enc:1` + `X-Enc-Compression:gzip` + `X-Burn-Secure:1`，并把 `options._v2Encrypted=true`。但 GET 无 body——设了 X-Enc 服务器会尝试按信封解析空 body → 401。**修复**：X-Enc/X-Enc-Compression 仅在 `options.body` 存在且非 multipart 时设置（同时 _v2Encrypted 才置 true）；X-Session/X-Burn-Secure 对 GET 保留（文档 h0.c 对所有请求设置）。
- **疑点 2（已修，诊断增强）**：401 分支原本不打印响应体，服务器拒绝原因完全不可见。**修复**：v2 401 时先读 body → 尝试 v2DecryptBody（信封则解密）→ `console.warn('[apiFetch] v2 401 响应体：...')`；同时**回退 v1 时清理全部 v2 专属头**（X-Sign/X-Ts/X-Nonce/X-Device-Id/X-Enc/X-Session/X-Burn-Secure/X-Enc-Compression），避免 v1 请求误带 X-Enc 触发类似问题。
- **自测**：node 全链路验证通过——签名 43 字符（base64 nopad）、信封 iv 24/mac 44 字符（带 padding，与 08 文档 flag=2 一致）、MAC 验证 + AES-CBC 解密一致。
- **下一步**：让用户跑一次看新打的 `v2 401 响应体` 日志——服务器返回的错误串（invalid_signature / missing session / 其它）直接指明根因。若响应体是明文错误而非信封，说明服务器对 GET 是明文校验，X-Enc 方向仍有偏差。

## v2 401 排查（第三轮：服务器响应体定位）

- **服务器响应体两个错误码（决定性）**：
  - `/v2/me` → `{"error":"missing session","code":"missing_session"}`：**握手未完成请求就发出**——旧逻辑 wsSessionId 为空时不设 X-Session 照样裸发 v2。
  - 其余全部（groups/list、friends、friends/requests、users/profile、groups/messages/v2、groups/members、groups/read）→ `{"error":"invalid signature","code":"bad_signature"}`：签名存在但**验签失败**——macKey 或拼接与服务器不一致。
- **已修**：apiFetch v2 分支改为——会话未就绪（无 X-Sign 或 getSessionId() 为空）时**不裸发 v2**，直接按端点熔断回退 v1（`v2FailedPaths.add`）；会话就绪才设 X-Session/X-Burn-Secure + 签名 + body 加密。
- **bad_signature 待文档确认（已向用户列清单）**：① 真实抓包样本（v2 请求完整头 + 登录请求头，本地复算签名对照）② 握手 client_pub 编码（SPKI 还是未压缩点 0x04||X||Y）③ **登录是否也走加密 + X-Session 与 token 的绑定机制**（dev2 流程：握手→加密登录带 X-Session→服务器把 session 与登录 token 关联；我们 v1 明文登录无 X-Session，服务器可能找不到 session 对应的 macKey）④ 签名 token 确切值（access_token 原文？带 Bearer？）⑤ X-Device-Id 是否参与验签。
- 节点：node --check OK。待文档补全后修正签名/登录链路。

## v2 401 根因找到（12-排查指南：两条传输路径互斥，混搭头导致 bad_signature）

- **新文档**：`12-v2签名机制与加密信封及bad_signature排查指南.md`（682 行）+ `07-安全机制与加密体系.md` + 02 网络层文档更新（dev2 版）。
- **决定性结论（§1.3/§8.2）**：v2 有**两条互斥传输路径**——
  - **h0.e 旧传输层**：有签名（X-Ts/X-Nonce/X-Sign/X-Device-Id），**无 X-Enc/X-Session/X-Burn-Secure**，body 明文，响应平铺明文 JSON。
  - **h0.c 新传输层**：有加密（X-Enc:1/X-Session/X-Enc-Compression/X-Burn-Secure），**无 X-Sign**，body 加密信封，URL 无 /v1 后缀。
  - 服务器实测按 h0.e 验签（返回明文 `{"error":"invalid signature","code":"bad_signature"}`），**不接受混搭**。
- **此前 bad_signature 根因**：我们同时带 X-Sign + X-Session + X-Burn-Secure（POST 还带 X-Enc）——把两条互斥路径的头塞一起，服务器按 X-Session 找 macKey 失败 → bad_signature。`missing_session`（/v2/me）是握手未完成时裸发无 session 的请求。
- **修复（app.js apiFetch v2 分支）**：v2 请求改走**纯 h0.e 路径**——只保留签名四件套（v2SignHeaders 返回的 X-Ts/X-Nonce/X-Sign/X-Device-Id）+ Authorization，body 明文不加密，**移除 X-Session/X-Burn-Secure/X-Enc/X-Enc-Compression 及 _v2Encrypted 标记**。会话未就绪（无 X-Sign 或 getSessionId 空）→ 按端点熔断回退 v1 不裸发。
- **签名算法确认（§4-§7）**：token=access_token 原文（不带 Bearer）；path 去查询参数；X-Ts 秒级；nonce 16B→base64 无填充（22 字符）；X-Device-Id 不参与签名；macKey=ECDH 派生 SHA256(truncated+"mac")，client_pub 用 SPKI(X.509 DER) 91 字节（与 Java getEncoded() 一致）——我们实现全部吻合。
- 验证：node --check OK。待回归：v2 请求只带签名四件套，若不再 bad_signature 则 v2 迁移打通；若仍 bad_signature 则 macKey 派生仍不一致（对照 §6.1 逐项排查）。

## v2 暂停：默认关闭（保留全部代码，oc_enable_v2='1' 启用）

- **第二轮实测**：纯 h0.e 签名路径（去掉 X-Session/X-Enc/X-Burn-Secure）后，错误从 bad_signature **变成全部 missing_session**——证明服务器**必须带 X-Session 才能验签**（h0.c 的 session 体系）。
- **交叉结论**：① 带 X-Session + 签名 → bad_signature（服务器找到 session 但 macKey 验签失败）② 不带 X-Session → missing_session。即服务器期望「X-Session + X-Sign 共存」，我们带 X-Session 时 macKey 仍不匹配 → **macKey 派生或 session 绑定（token↔session）与服务器不一致**，需抓包级真实样本才能定死。
- **决定（用户指示）**：先放弃 v2，`v2Enabled` 默认 **false**（oc_enable_v2='1' 启用）；V1_TO_V2 映射/签名/信封加密解密/端点熔断代码全保留，不删。
- 验证：node --check OK。客户端回归 v1 稳定运行。
