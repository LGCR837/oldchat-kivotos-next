- **诊断：头像/媒体其实没缓存（用户报告灰色闪烁 + 请求量异常）**：
  - 代码里唯一的"缓存"是 `mediaUrlCache`（`src/app.js`~300 的 `Map`），只 memoize `resolveMediaUrl` 的**字符串结果**，省字符串拼接 CPU，**对网络请求/图片字节零作用**。没有 blob 缓存、没有 `Image()` 预加载注册表、没有任何内存位图缓存。
  - 唯一能缓存图片字节的是浏览器/WebView HTTP 缓存，但两个媒体源都返回 `Cache-Control: no-store`（curl -I 实测 `60.205.94.101:8080` 与 `files.mcl0.dpdns.org` 均 `no-store`）→ HTTP 缓存被禁止存储 → 每个 `<img>` 重新出现都重新下载 → 自己头像第二次出现短暂灰（`background:var(--border)` 占位直到加载）。
  - 媒体候选降级链（`src/app.js`~276 全局 error 监听）默认 4 候选源，任一头像瞬时失败就换源重抓 → 单个头像可发 2~4 请求；叠加频繁整页重渲染（切会话/在线状态/typing/WS 重连都重建 `<img>`）→ 请求量爆炸，符合"腐竹公开数据中位列第一、官方客户端 1.5 倍请求、但用户仅 1/5（≈7.5 倍/用户）"。
  - 结论：需做**客户端真实图片缓存**（fetch→blob: 或 Image() 预热，按原 URL 存 Map，渲染用 blob URL；唯一 URL 每次会话只抓一次；并给离屏头像加 `loading=lazy`）。可同时根治灰色闪烁与请求量问题。尚未实现，待用户确认。

- **修复 MediaCache 原生请求泄漏（紧急，腐竹私信要求降服务器压力）**：
  - 用户此前已加了真正的媒体缓存（`src/app.js`~335 IIFE：IndexedDB + memCache Map + MutationObserver，window.__MediaCache 已 init，白名单齐全，tauriHttpFetch 返回标准 Response）。但**缓存一直在跑却没压住请求**——根因是泄漏：模板把 `<img src="http://60.205…/x.png">` 直接写进 DOM，observer 异步换成 blob，但"换"之前浏览器已向媒体服务器发起原生请求；后端 `Cache-Control: no-store` 让这次请求缓存不住 → 每次重渲染都白打一次原生 http，再被换 blob。媒体源抖动时全局 `error` 监听还会触发候选链（单头像 2~4 请求）。
  - 修复（仅改 MediaCache IIFE，不碰 30+ 渲染点）：① 新增 `MEDIA_PLACEHOLDER`（1x1 透明 GIF），`processElement` 拦截到 `<img src>` 的**第一时间**立即 `setAttribute('src', MEDIA_PLACEHOLDER)` 抢在浏览器原生加载前替换，彻底阻断原生请求；② 候选源降级收进 `fetchAndStore` 内部（`mediaCandidateUrls()` 生成候选 + `fetchOne()` 单源抓取，每个唯一 URL 只抓一次并缓存成功 blob），不再依赖全局 error 监听放大；③ callback 处理：blob→用 blob（零网络），失败→恢复 `val` 远程地址降级为旧行为（全局 error 监听兜底）。效果：每个唯一图片每会话仅 1 次请求（首屏走 blob 也消除灰色闪烁），重渲染零网络。node --check 通过。**已提交并推送**：commit `4a10f1e`「Fix MediaCache native request leak + lazy-load comment counts」，含 MediaCache 修复 + 评论懒加载 + 本周期 UI（QQ Blue/系统通知页/Typing 动画/标题渐变/横向溢出修复），`git push origin main` → `4fa4f49..4a10f1e`。

- **Bug fix: 视频（ArtPlayer）完全不显示**（`src/app.js`）：下午加的 ArtPlayer 视频消息一直没验证，用户反馈「一片空白、只有个悬浮的暂停按钮」。两个根因：① **容器宽度塌陷**：`.video-message` 用 `max-width:200px;width:100%;aspect-ratio:16/9` 撑高度，但父气泡 `.message.other .message-bubble{width:fit-content}` 让 `width:100%` 解析成 0 → `aspect-ratio` 算出高度 0 → 播放器盒子塌成 0 高，视频不可见，只剩绝对定位的暂停按钮飘着。改为 `width:200px;max-width:100%;aspect-ratio:16/9`（确定宽度，打破 fit-content 循环）。② **MediaCache 误伤 `<video>`**：我的缓存层把 ArtPlayer 内部 `<video src>` 也拦截（先换 1x1 透明 GIF 占位、再异步换整段视频 blob），既打断播放器加载又无意义地把整段视频读进内存。在 `processElement` 加 `if (tag==='video'||tag==='source') return;`，并从 observer 选择器（`img,audio,video,source,track`→`img,audio,track`）与初次扫描里移除 video/source。**关键经验**：MediaCache 只应管 `<img>`/`<audio>` 这类静态资源；`<video>` 等由播放器原生流式加载，绝不能被缓存层接管。ArtPlayer 的 CSS 是自带的（`artplayer.js` 内 `Wt` 变量字符串 + `createElement('style')` 注入 head），无需额外 css 文件。
