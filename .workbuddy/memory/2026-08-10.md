- **诊断：头像/媒体其实没缓存（用户报告灰色闪烁 + 请求量异常）**：
  - 代码里唯一的"缓存"是 `mediaUrlCache`（`src/app.js`~300 的 `Map`），只 memoize `resolveMediaUrl` 的**字符串结果**，省字符串拼接 CPU，**对网络请求/图片字节零作用**。没有 blob 缓存、没有 `Image()` 预加载注册表、没有任何内存位图缓存。
  - 唯一能缓存图片字节的是浏览器/WebView HTTP 缓存，但两个媒体源都返回 `Cache-Control: no-store`（curl -I 实测 `60.205.94.101:8080` 与 `files.mcl0.dpdns.org` 均 `no-store`）→ HTTP 缓存被禁止存储 → 每个 `<img>` 重新出现都重新下载 → 自己头像第二次出现短暂灰（`background:var(--border)` 占位直到加载）。
  - 媒体候选降级链（`src/app.js`~276 全局 error 监听）默认 4 候选源，任一头像瞬时失败就换源重抓 → 单个头像可发 2~4 请求；叠加频繁整页重渲染（切会话/在线状态/typing/WS 重连都重建 `<img>`）→ 请求量爆炸，符合"腐竹公开数据中位列第一、官方客户端 1.5 倍请求、但用户仅 1/5（≈7.5 倍/用户）"。
  - 结论：需做**客户端真实图片缓存**（fetch→blob: 或 Image() 预热，按原 URL 存 Map，渲染用 blob URL；唯一 URL 每次会话只抓一次；并给离屏头像加 `loading=lazy`）。可同时根治灰色闪烁与请求量问题。尚未实现，待用户确认。
